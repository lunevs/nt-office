# Наш офис

Мобильное веб-приложение для церковного офиса. Требования и этапы: [SPEC.md](SPEC.md). Текущий статус: [STATUS.md](STATUS.md).

Реализованы этапы 1–4: учётные записи и управление доступом; компактный дневной календарь и разовые мероприятия; согласование, отмена, конфликты и скрытие деталей; еженедельные серии. Личные сообщения будут добавлены на следующем этапе. Работа и проверка пока только локально.

Стек: Django 5.2 LTS, PostgreSQL 17, Gunicorn, WhiteNoise. Серверный HTML и CSS, без сборки фронтенда и внешних шрифтов. Зависимости закреплены в `requirements.txt`.

## Локальный запуск в Docker

1. Скопируйте `.env.example` в `.env`.
2. Замените `SECRET_KEY`, `POSTGRES_PASSWORD` и `BOOTSTRAP_ADMIN_PASSWORD` случайными значениями. Для локального `POSTGRES_PASSWORD` используйте буквы и цифры: он включается в URL подключения.
3. Запустите:

```sh
docker compose up --build -d
```

Откройте <http://localhost:8000>. Логин первого администратора задаётся через `BOOTSTRAP_ADMIN_LOGIN`. При первом входе необходимо сменить пароль. После создания администратора удалите из `.env` переменную `BOOTSTRAP_ADMIN_PASSWORD`: команда первоначального создания не меняет существующие учётные записи.

В текущей рабочей копии `.env` уже создан с уникальными случайными секретами и правами доступа `0600`. Он не включается в Git и Docker-образ. Начальный локальный пароль доступен в этом файле.

```sh
docker compose logs --tail=100 web
docker compose exec web python manage.py test
docker compose restart
```

Данные сохраняются в томе `postgres_data`. `docker compose down` сохраняет том; **`docker compose down -v` удаляет базу**.

Локальный Compose включает `DEBUG=true` и HTTP только на loopback. Этот режим не использовать в Railway.

## Порядок публикации

Сначала заказчик проверяет приложение локально. После проверки — размещение исходников на GitHub. Развёртывание на Railway выполняется только после этого и по отдельному указанию заказчика.

## Развёртывание в Railway

1. Создайте проект и добавьте PostgreSQL. Убедитесь, что у PostgreSQL подключён постоянный том.
2. Создайте сервис приложения из этого каталога или репозитория. Railway использует `Dockerfile` и `railway.toml`.
3. Установите переменные сервиса приложения:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | Ссылка Railway `${{Postgres.DATABASE_URL}}` (имя сервиса БД может отличаться) |
| `SECRET_KEY` | Уникальный случайный секрет, минимум 50 символов |
| `DEBUG` | `false` |
| `BOOTSTRAP_ADMIN_LOGIN` | Логин первого администратора |
| `BOOTSTRAP_ADMIN_FIRST_NAME` | Имя администратора |
| `BOOTSTRAP_ADMIN_LAST_NAME` | Фамилия администратора |
| `BOOTSTRAP_ADMIN_PASSWORD` | Сильный временный пароль, минимум 10 символов |

4. Сгенерируйте публичный домен. `RAILWAY_PUBLIC_DOMAIN` автоматически добавляется в допустимые хосты и доверенные CSRF origins. Для своего домена добавьте `ALLOWED_HOSTS` (хосты через запятую) и `CSRF_TRUSTED_ORIGINS` (полные HTTPS origins через запятую). Сохраните `healthcheck.railway.app` в `ALLOWED_HOSTS`.
5. Разверните сервис. При старте применяются миграции, создаётся первый администратор, собирается статика и запускается Gunicorn на `PORT`, заданном Railway.
6. Проверьте `/healthz/`, вход и регистрацию. Healthcheck проверяет доступность базы и возвращает 503 при её недоступности.
7. Войдите администратором, смените временный пароль и удалите `BOOTSTRAP_ADMIN_PASSWORD` из переменных Railway.

В production приложение требует PostgreSQL и `SECRET_KEY`, использует HTTPS, защищённые cookies и CSRF. Контейнер работает от непривилегированного пользователя. Сброс пароля завершает прежние сессии пользователя. После 10 попыток входа для логина действует ограничение на 15 минут, сохранённое в БД.

При нескольких репликах миграции и создание администратора следует вынести в единственную pre-deploy операцию. На первом этапе используется одна реплика приложения с двумя процессами Gunicorn.

## Резервное копирование

Локальная копия базы:

```sh
docker compose exec -T db pg_dump -U office -d office -Fc > office-backup.dump
```

Храните копии отдельно от хоста и не добавляйте их в репозиторий. Для Railway включите доступный в вашем тарифе механизм резервных копий тома PostgreSQL и проверьте восстановление. Логическую копию также можно получить через `pg_dump`, используя URL внешнего подключения Railway из защищённой среды; не помещайте пароль в командную строку или историю shell.

Для проверки восстановления используйте отдельную пустую базу, не рабочую:

```sh
docker compose exec -T db createdb -U office office_restore
docker compose exec -T db pg_restore -U office -d office_restore < office-backup.dump
```

## Проверка первого этапа

Автотесты проверяют регистрацию с закрытым доступом до активации, права администратора, уникальность логина без учёта регистра, защиту POST от CSRF, ограничение входа, качество паролей, сброс с завершением сессий, обязательную смену временного пароля и повторный запуск создания администратора.

Ручной сценарий:

1. Зарегистрировать участника и проверить отказ во входе до активации.
2. Войти администратором, открыть «Управление», активировать участника.
3. Войти участником и открыть профиль.
4. Сбросить пароль участника администратором; проверить прекращение старой сессии.
5. Войти с временным паролем и сменить его; до смены другие экраны недоступны.
6. Перезапустить контейнеры и проверить сохранение учётных записей и входа.
7. Проверить мобильный экран: формы в одну колонку, читаемые ошибки, доступные кнопки и отсутствие горизонтальной прокрутки.

Официальные справочные материалы: [Railway: Django](https://railway.com/guides/django), [Railway: healthchecks](https://docs.railway.com/deployments/healthchecks), [Django: deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).


## Проверка третьего этапа

1. Создайте мероприятие: оно сразу появляется в календаре со статусом «На подтверждении». Существующие мероприятия при обновлении также получают этот статус.
2. Администратором откройте «Управление» → «На подтверждении» → карточку встречи → «Подтвердить».
3. Автором измените время, дату или помещения подтверждённой встречи: статус вернётся на подтверждение. Изменение названия или количества людей статус не сбрасывает; перенос администратором тоже не сбрасывает его.
4. Создайте пересекающиеся встречи в одной комнате: обе получат отметку конфликта. В разных комнатах или с окончанием одной точно в начале другой конфликта нет. Подтверждать конфликтующие встречи разрешено.
5. Включите «Private (не публиковать детали)». Другой пользователь видит «Занято», дату и время, помещения, статус и ответственного. Название и количество людей недоступны также в `/api/events/<id>/`. Автор и администратор видят детали. Указанный ответственный не получает автоматически права автора.
6. Автором или администратором откройте редактирование карандашом справа от времени и нажмите «Отменить мероприятие». Она исчезнет из временной шкалы и ближайших встреч профиля, перестанет создавать конфликты и появится в профиле автора по кнопке «Мои отменённые мероприятия» и у администратора по кнопке «Все отменённые мероприятия» в управлении (сначала последние отмены).
7. В отменённой встрече можно исправить данные, затем нажать «Отправить на подтверждение». До отправки встреча остаётся отменённой.

В профиле показываются максимум три ближайшие ещё не завершившиеся встречи, где пользователь ответственный. Имя и логин редактируются карандашами. Пароль пользователя — минимум 5 символов, администратора — 10; похожесть на личные данные не проверяется.


## Проверка четвёртого этапа

1. Создайте встречу с «Повторять раз в неделю» и датой «Повторять до». Конечная дата включается, если совпадает с днём недели первой встречи. После создания открывается ближайший день серии не раньше сегодняшнего (для полностью прошедшей серии — последняя встреча).
2. Откройте карандашом одну встречу серии и выберите «Только эта встреча». Перенесите её; соседние вхождения не должны измениться.
3. На встрече из середины серии выберите «Эта и все последующие встречи». Измените время, помещения или дату. Более ранние вхождения сохраняются. Даты последующих сдвигаются на ту же разницу дней; их индивидуальные переносы сохраняются.
4. В форме редактирования отмените одну встречу или её и последующие. Проверьте календарь и список отменённых. Повторно отправить можно с той же областью действия.
5. Подтвердите встречу администратором. Перенос автором должен вернуть изменённые подтверждённые вхождения на согласование. Перенос администратором статус не сбрасывает; отменённые вхождения при редактировании не восстанавливаются автоматически.
6. Создайте конфликт только для одного вхождения и проверьте независимые отметки пересечений. Серия через переход на летнее/зимнее время должна сохранять одинаковое местное время начала.

В одной серии максимум 520 встреч. Указание ответственного не даёт ему права изменять серию. При подтверждении можно выбрать одну встречу (по умолчанию) или эту и все последующие на согласовании; отменённые и уже подтверждённые пропускаются. В управлении серия представлена одной карточкой с количеством встреч, диапазоном дат и количеством пересечений.


Уточнение согласования серии: в карточке нет выбора области для подтверждения и отказа — эти действия применяются ко всей серии, независимо от открытого вхождения. Подтверждаются только ожидающие согласования; отменённые не восстанавливаются. При редактировании выбор одной встречи или этой и последующих сохранён. Отмена из формы редактирования — две кнопки в ряд: «Отменить это событие» и «Отменить всю серию».
