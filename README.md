# Наш офис

Мобильное веб-приложение для церковного офиса. Требования и этапы: [SPEC.md](SPEC.md). Текущий статус: [STATUS.md](STATUS.md).

Реализованы этапы 1–5: учётные записи и управление доступом; компактный дневной календарь и разовые мероприятия; отмена, восстановление, конфликты и скрытие деталей; еженедельные серии; личные сообщения с отметками непрочитанных. Перед запуском требуется итоговая ручная проверка заказчиком. Работа и проверка пока только локально.

Стек: Django 5.2 LTS, PostgreSQL 17, Gunicorn, WhiteNoise. Серверный HTML и CSS, без сборки фронтенда и внешних шрифтов. Зависимости закреплены в `requirements.txt`.

## Локальный запуск в Docker

1. Скопируйте `.env.example` в `.env`.
2. Замените `SECRET_KEY`, `POSTGRES_PASSWORD` и `BOOTSTRAP_ADMIN_PASSWORD` случайными значениями. Для локального `POSTGRES_PASSWORD` используйте буквы и цифры: он включается в URL подключения.
3. Запустите:

```sh
docker compose up --build -d
```

Откройте <http://localhost:8000>. Логин первого администратора задаётся через `BOOTSTRAP_ADMIN_LOGIN`. При первом входе необходимо сменить пароль. После создания администратора удалите из `.env` переменную `BOOTSTRAP_ADMIN_PASSWORD`: команда первоначального создания не меняет существующие учётные записи.

В текущей рабочей копии `.env` уже создан с уникальными случайными секретами и правами доступа `0600`. Он не включается в Git и Docker-образ. Начальный локальный пароль доступен в этом файле.

```sh
docker compose logs --tail=100 web
docker compose exec web python manage.py test
docker compose restart
```

Данные сохраняются в томе `postgres_data`. `docker compose down` сохраняет том; **`docker compose down -v` удаляет базу**.

Локальный Compose включает `DEBUG=true` и HTTP только на loopback. Этот режим не использовать в Railway.

## Порядок публикации

Сначала заказчик проверяет приложение локально. После проверки — размещение исходников на GitHub. Развёртывание на Railway выполняется только после этого и по отдельному указанию заказчика.

## Развёртывание в Railway

1. Создайте проект и добавьте PostgreSQL. Убедитесь, что у PostgreSQL подключён постоянный том.
2. Создайте сервис приложения из этого каталога или репозитория. Railway использует `Dockerfile`. Устаревший `railway.toml` удалён; параметры запуска сохранены в настройках сервиса (таблица ниже).
3. Установите переменные сервиса приложения:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | Ссылка Railway `${{Postgres.DATABASE_URL}}` (имя сервиса БД может отличаться) |
| `SECRET_KEY` | Уникальный случайный секрет, минимум 50 символов |
| `DEBUG` | `false` |
| `BOOTSTRAP_ADMIN_LOGIN` | Логин первого администратора |
| `BOOTSTRAP_ADMIN_FIRST_NAME` | Имя администратора |
| `BOOTSTRAP_ADMIN_LAST_NAME` | Фамилия администратора |
| `BOOTSTRAP_ADMIN_PASSWORD` | Сильный временный пароль, минимум 10 символов |
| `TELEGRAM_BOT_TOKEN` | Токен бота от @BotFather (вход через Telegram, мини-приложение, уведомления) |
| `TELEGRAM_BOT_USERNAME` | Имя бота без @, например `new_territory_schedule_bot` |
| `SITE_URL` | Необязательно: публичный HTTPS-адрес, если домен свой (иначе берётся `RAILWAY_PUBLIC_DOMAIN`) |

4. Сгенерируйте публичный домен. `RAILWAY_PUBLIC_DOMAIN` автоматически добавляется в допустимые хосты и доверенные CSRF origins. Для своего домена добавьте `ALLOWED_HOSTS` (хосты через запятую) и `CSRF_TRUSTED_ORIGINS` (полные HTTPS origins через запятую). Сохраните `healthcheck.railway.app` в `ALLOWED_HOSTS`.
5. Разверните сервис. При старте применяются миграции, создаётся первый администратор, собирается статика и запускается Gunicorn на `PORT`, заданном Railway.
6. Проверьте `/healthz/`, вход и регистрацию. Healthcheck проверяет доступность базы и возвращает 503 при её недоступности.
7. Войдите администратором, смените временный пароль и удалите `BOOTSTRAP_ADMIN_PASSWORD` из переменных Railway.

В production приложение требует PostgreSQL и `SECRET_KEY`, использует HTTPS, защищённые cookies и CSRF. Контейнер работает от непривилегированного пользователя. Сброс пароля завершает прежние сессии пользователя. После 10 попыток входа для логина действует ограничение на 15 минут, сохранённое в БД.

При нескольких репликах миграции и создание администратора следует вынести в единственную pre-deploy операцию. На первом этапе используется одна реплика приложения с двумя процессами Gunicorn.

## Telegram: вход, мини-приложение и уведомления

Без `TELEGRAM_BOT_TOKEN` приложение работает как обычно: вход по логину и паролю, без бота.

После публикации на HTTPS-адресе:

1. Бот настраивается сам при каждом запуске сервера (`start.sh` вызывает `python manage.py telegram_setup --if-configured`). Команда включает вебхук бота (`/telegram/webhook/`, с секретным заголовком), кнопку меню «Календарь» с мини-приложением (`/tg/`) и команду /start. Без токена шаг пропускается, ошибка Telegram не мешает запуску. Вручную команду можно выполнить так же, без флага.
2. В @BotFather: `/setdomain` — домен сайта (нужен для кнопки «Войти через Telegram» на сайте); «Configure Mini App» или `/newapp` — адрес `https://<домен>/tg/`, чтобы приложение открывалось и по ссылке `t.me/<бот>/<приложение>`.
3. Проверьте: откройте бота → «Календарь». Непривязанный Telegram может создать аккаунт (данные подставлены из Telegram) или один раз войти по логину, чтобы привязать существующий.

Бронировать можно сразу после регистрации. Неподтверждённый аккаунт ограничен: одна встреча в день, не дольше 2 часов, без повтора. Подтверждение он запрашивает сам, администратор подтверждает в «Управлении» или кнопкой «Подтвердить» в сообщении бота. Уведомления бота: новые сообщения, изменения и отмены встреч, где человек ответственный; администраторам ещё запросы на подтверждение и «Нужен ключ». Каждое уведомление отключается в профиле.

Утренняя сводка «Сегодня в офисе»: каждый день в 8:00 (часовой пояс приложения) бот присылает в личный чат встречи на день с кнопкой «Открыть расписание». Получают все активные пользователи с привязанным Telegram; отключается в профиле («Утренняя сводка»). В дни без встреч сводки нет. Рассылку запускает фоновый поток в процессе Gunicorn (`TELEGRAM_DIGEST_SCHEDULER=1` в `start.sh`). Если сервер перезапустился позже 8:00, сводка уйдёт до 11:00. Повтор за день исключён записью `DailyDigest` в базе. Команда `/today` в чате с ботом показывает сводку в любой момент.

Telegram Web открывает мини-приложение во фрейме, поэтому вместо `X-Frame-Options: DENY` отдаётся `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org`.

## Работа без сети и обновления (PWA)

`/sw.js` — service worker с областью действия на весь сайт.

- **Статика** заранее кэшируется. Адреса файлов содержат хэш, поэтому из кэша они отдаются без запроса к серверу.
- **Страницы** загружаются из сети. После каждого открытия сохраняются расписание, страницы встреч, отменённые встречи, сообщения и профиль, не больше 60 страниц.
- **Без сети** показывается последняя сохранённая копия и тост «Нет сети · показываем сохранённое расписание». Кнопка «+» приглушена, формы не отправляются. Ссылки на несохранённые страницы не открываются. Когда сервер снова отвечает (проверка `/healthz/` каждые 10 секунд), страница обновляется сама.
- **Не сохраняются** формы, вход и регистрация, Telegram-страницы и «Управление», где показываются временные пароли.
- **Выход из аккаунта** или открытие страницы входа удаляет сохранённые страницы.
- **Новая версия.** Если при деплое изменилась статика, браузер получает новый service worker. Появляется тост «Доступна новая версия», кнопка «Обновить» включает новую версию и перезагружает страницу.

## Резервное копирование

Локальная копия базы:

```sh
docker compose exec -T db pg_dump -U office -d office -Fc > office-backup.dump
```

Храните копии отдельно от хоста и не добавляйте их в репозиторий. Для Railway включите доступный в вашем тарифе механизм резервных копий тома PostgreSQL и проверьте восстановление. Логическую копию также можно получить через `pg_dump`, используя URL внешнего подключения Railway из защищённой среды; не помещайте пароль в командную строку или историю shell.

Для проверки восстановления используйте отдельную пустую базу, не рабочую:

```sh
docker compose exec -T db createdb -U office office_restore
docker compose exec -T db pg_restore -U office -d office_restore < office-backup.dump
```

## Проверка первого этапа

Автотесты проверяют регистрацию с немедленным доступом и блокировку администратором, права администратора, уникальность логина без учёта регистра, защиту POST от CSRF, ограничение входа, качество паролей, сброс с завершением сессий, обязательную смену временного пароля и повторный запуск создания администратора.

Ручной сценарий:

1. Зарегистрировать участника и проверить немедленный вход в календарь.
2. Администратором открыть «Управление» и нажать замок у участника: вход и доступ через прежние сессии должны закрыться.
3. Разблокировать участника замком и войти с прежним паролем. Старые сессии не должны восстановиться.
4. Сбросить пароль участника администратором; проверить прекращение старой сессии.
5. Войти с временным паролем и сменить его; до смены другие экраны недоступны.
6. Перезапустить контейнеры и проверить сохранение учётных записей и входа.
7. Проверить мобильный экран: формы в одну колонку, читаемые ошибки, доступные кнопки и отсутствие горизонтальной прокрутки.

Официальные справочные материалы: [Railway: Django](https://railway.com/guides/django), [Railway: healthchecks](https://docs.railway.com/deployments/healthchecks), [Django: deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).


## Мероприятия без согласования

С 17 ноября 2026 года согласование мероприятий удалено. Любой активный зарегистрированный пользователь создаёт разовую встречу или серию сразу в статусе «Запланировано». Переносы и изменения действуют сразу. Согласование новых учётных записей тоже удалено: регистрация сразу открывает доступ. В управлении есть список всех пользователей с замком блокировки/разблокировки.

Проверка:

1. Создайте встречу обычным пользователем: она сразу видна в календаре и не требует действий администратора.
2. Измените дату, время и помещения: встреча остаётся запланированной. Если есть пересечение по времени и общим помещениям, появляется отметка конфликта, но сохранение разрешено.
3. Карандаш справа от времени открывает редактирование. Внизу формы — отмена; у серии две кнопки в ряд: «Отменить это событие» и «Отменить всю серию».
4. Отменённые встречи не занимают календарь и не создают конфликтов. В профиле доступны свои отменённые встречи, в управлении — общий список. Сначала показываются последние отмены.
5. Откройте отменённую встречу и нажмите «Восстановить мероприятие»: она сразу возвращается в календарь, без подтверждения. У серии можно восстановить выбранное вхождение или его и последующие отменённые встречи.
6. Private скрывает название и количество людей от всех, кроме автора и администратора, в том числе в API. Ответственный не получает права автора автоматически.

Миграция `0008_alter_event_status_event_event_valid_status` переводит прежние `pending` и `confirmed` в `active`, не меняя отменённые встречи, связи с помещениями или содержимое бронирований. Рабочие статусы в API: `active`, `cancelled`.

## Проверка еженедельных серий

При создании отметьте «Повторять раз в неделю» и укажите конечную дату включительно (до 520 встреч). Без галочки конечная дата серая и недоступна.

При редактировании можно изменить одну встречу либо её и все последующие. Более ранние вхождения сохраняются; даты последующих сдвигаются на одинаковую разницу дней. При отмене серии доступны две отдельные кнопки. Редактирование отменённой встречи не восстанавливает её автоматически. Местное время сохраняется при сезонном переводе часов, конфликты учитываются отдельно для каждого вхождения.

## Проверка пятого этапа

1. Двумя активными пользователями откройте «Сообщения» → «Написать», найдите друг друга по имени или логину и обменяйтесь текстом. Максимум сообщения — 5000 символов. Пустые сообщения не отправляются.
2. Оставьте диалог открытым: новые сообщения появляются без перезагрузки (проверка каждые 5 секунд, пока страница видима). История хранится в PostgreSQL; старые сообщения доступны по ссылке «Более ранние сообщения».
3. До открытия диалога проверьте счётчик непрочитанных в навигации и списке переписок. После просмотра диалога сообщения отмечаются прочитанными; другие диалоги остаются непрочитанными.
4. Войдите третьим пользователем, включая администратора: чужая переписка отсутствует и не выдаётся через запросы обновления диалога.
5. Откройте карточку мероприятия и нажмите конверт справа от имени ответственного или автора. Открывается личный диалог без автоматической отправки. Для самого себя и неактивного пользователя конверт отсутствует; скрытый автор не раскрывается.
6. Проверьте на телефоне ввод многострочного текста, экранную клавиатуру, доступность кнопки отправки и нижней навигации. При ошибке обновления диалога показывается сообщение с предложением проверить соединение или обновить страницу.

Вложения, общий чат, обсуждения событий, внешние уведомления и напоминания не добавлены. Неактивные пользователи не доступны для новых диалогов. Сообщения не публикуются в календаре. При отправке используется серверная проверка сессии и CSRF, в отображении — экранирование текста.


Мероприятия всех активированных пользователей сразу запланированы, согласование отсутствует.


## Production Railway

Адрес: https://web-production-2ce564d2.up.railway.app

Проект `nt-office`, сервис приложения `web`, база `Postgres` с постоянным томом. Сервис связан с GitHub `lunevs/nt-office`, ветка `main`: следующие push в эту ветку запускают автоматическое развёртывание.

| Настройка сервиса web | Значение |
|---|---|
| Dockerfile path | `/Dockerfile` |
| Start command | По умолчанию из Dockerfile: `/app/start.sh` |
| Healthcheck path | `/healthz/` |
| Healthcheck timeout | 180 секунд |
| Restart policy | `ON_FAILURE`, до 5 повторов |
| Реплики | 1 |
| Порт | 8000 |

`railway.toml` больше не используется. При создании нового сервиса эти параметры нужно установить в Railway. Dockerfile обнаруживается автоматически. См. [официальную документацию](https://docs.railway.com/config-as-code).

Production-база отдельная от локальной: тестовые пользователи, встречи и сообщения автоматически не переносятся. Начальный production-пароль администратора находится только в локальном `.env.railway` (не в Git); после первого входа требуется смена пароля. Передавайте пароль лично. После создания администратора переменная `BOOTSTRAP_ADMIN_PASSWORD` удалена из Railway; начальный пароль остаётся в локальном `.env.railway` до смены пользователем. Команда bootstrap не меняет существующие учётные записи.


На текущем тарифе Railway (Hobby) настройка резервных копий тома недоступна: API требует Pro. Регулярное резервное копирование production пока не настроено. Заказчик разрешил локальное сохранение production-копий в `backups/` (папка исключена из Git). Первая копия создана через Railway SSH и проверена `pg_restore --list`; это разовая операция, не регулярное расписание.


Блокировка пользователей не удаляет их встречи или сообщения и не меняет пароль. Сессионная версия отзывается при блокировке, поэтому после разблокировки требуется новый вход. Администраторов блокировать нельзя. Старые неактивные аккаунты сохраняются как заблокированные до ручной разблокировки.


Разовую production-копию можно создать командой `python3 scripts/backup_production.py` при установленном Railway CLI и запущенном Docker. Скрипт использует связанный проект Railway и сервис `Postgres`, сохраняет архив в исключённую из Git папку `backups/` с правами 0600 и проверяет его через `pg_restore --list`.
